# 未披露设施的身份核查采集资料约定

同场址建筑身份仍待核。normal.json 描述两份来源，conflict.json 用同一身份和版次给出不同原文，identity.json 演示多栋建筑、别名、同址设施、轮廓晚到与许可更正。原文、解释记录和可见状态需要一致，不能用合成资料推断现实设施或排放。

## 来源清单（manifest）

每个响应除 `file`、`status`、`bytes`、`sha256` 外必须携带 `acquired_at`（ISO 8601 取得时间）；缺失或不可解析的来源在传输层即被拒绝，不会入账。

## 来源线与版次

来源记录按身份分三条线：`candidate`（商业名单等线索）、`support`（地方许可，含 `permit` 字段）、`outline`（卫星轮廓，含 `footprint` 字段）。同一线内同一身份的新版次（如许可更正 `r2`）取代旧版次参与解析，旧版次保留在账本中并列入 `superseded`。同一身份同一版次原文冲突仍由账本原子拒绝。

## 已核实与候选

地块、运营主体、建筑归属、别名四类关系需两种以上来源线佐证方为 `verified`，否则为 `candidate`；同址设施按共享地块推导，成员地块依据均已核实才为 `verified`。建筑或别名被多个设施主张时记为 `conflict`。未关联到设施线索的轮廓列入 `unlinked_outlines`，不产生任何设施结论。

## 覆盖总体

设施计入 `coverage.covered` 需地块与运营主体依据均已核实；来源不足的设施列入 `coverage.insufficient` 并附原因，不计入 `covered_count`，也不会从视图中隐去。

## 期次回查

每次登记分配单调期次（epoch）。`inspect --as-of N` 仅使用第 N 期（含）之前登记的来源解析身份关系与缺口；`epochs` 列出各期的取得时间、地址与原文摘要，供回查定位。
